# Как устроен multiple-apps

Гайд для того, кто открыл репо впервые: какие бывают пакеты, куда класть код и почему что-то «не подхватывается».

---

## Три вида пакетов

| Вид | Кто | Как узнать | Как подключают |
|-----|-----|------------|----------------|
| **Приложение** | `apps/f1` | запускается через `dev:*`, есть страницы, деплоится само | никто не подключает |
| **Слой** | `packages/ui` | сам не запускается, вход пакета — `nuxt.config.ts` | `extends: ['@multi/ui']` |
| **Библиотека** | `packages/utils`, `packages/eslint-config` | обычный TS/JS без Nuxt | `import ... from '@multi/utils'` |

Вход пакета (`main` или `exports` в `package.json`) отвечает на вопрос «какой файл получит тот, кто обратится к пакету по имени». У слоя это `nuxt.config.ts`, у библиотеки — `index.ts`. Поэтому в `extends` можно писать только слои.

```
  f1        ← приложение: страницы, каркас, тема, PWA, серверные ручки
  ui        ← кит: Nuxt UI, Tailwind, общие компоненты
  utils     ← функции и типы без Vue
```

---

## Куда класть код

Задай вопросы по порядку, первый «да» говорит, куда:

1. Это про конкретное приложение (F1, пилоты, OpenF1, каркас F1)? → `apps/f1`
2. Это кирпичик без смысла, который можно поставить куда угодно (кнопка, бейдж, карточка)? → `packages/ui/app/...`
3. Это функция или тип без Vue? → `packages/utils`

Не уверен — клади в `apps/f1`. Понадобится второму приложению — перенесёшь в `ui`.

| Что | Куда |
|-----|------|
| страница | `apps/f1/app/pages/...` |
| каркас (шапка, сайдбар, статус-бар) | `apps/f1/app/layouts/default.vue` + `apps/f1/app/components/` |
| тема и шрифты F1 | `apps/f1/app/assets/css/main.css` — единственная точка входа Tailwind: `@import "@multi/ui/css"`, ниже `@theme` и `@utility`. Слой `ui` свой CSS в приложение сам не подключает, иначе `@theme` приложения не попал бы в сборку |
| серверные ручки | `apps/f1/server/api/f1/...` — префикс `/api/f1`, чтобы ручки будущих приложений не пересеклись |
| витрина компонентов кита | `packages/ui/.playground` — наружу не уходит |

## Кто побеждает при конфликте

Сильнее тот, кого **запускаешь**, слой (`ui`) — слабее.

| Что совпало | Как разрешается |
|-------------|-----------------|
| файл с тем же путём (`app.vue`, `components/PriceTag.vue`) | побеждает один целиком |
| `nuxt.config`, `app.config` | сливаются по ключам, при конфликте побеждает приложение |

Посмотреть, откуда взят компонент: `.nuxt/components.d.ts` приложения.

## Зависимости

- **Пакет объявляет всё, что импортирует сам.** pnpm строгий: зависимости ui не видны f1, даже если f1 стоит на ui.
- **Модули Nuxt приходят через слой.** `@nuxt/ui` объявлен в ui, приложение его не дублирует: Nuxt находит модуль по цепочке `extends`, а не в `node_modules` приложения.
- **Команды, которые запускаются в папке пакета** (`eslint`, `vue-tsc`), ищут себя в `node_modules` этого пакета — поэтому `eslint` и `@multi/eslint-config` есть в каждом пакете с `lint`.
- **Версии** — один раз в `catalog` в `pnpm-workspace.yaml`, в пакетах `"catalog:"`.
- Внутренние пакеты — `"workspace:*"`, импорт только по имени пакета, не относительным путём (`../../packages/...`).

Правило «кто запускает, тот и ищет»: запускает Nuxt — он ходит по слоям; запускаешь команду в папке пакета — она ищет в этом пакете и выше до корня.

## Turbo

| Задача | Настройка | Что значит |
|--------|-----------|------------|
| `typecheck` | `dependsOn: ["^typecheck"]` | правка в ui перепроверяет f1 |
| `lint` | `inputs` + `$TURBO_ROOT$/packages/eslint-config/**` | lint пакета зависит от своих файлов и от общих правил, но не от кода соседей |
| `lint:fix` | `cache: false` | меняет файлы — кэшировать нельзя |
| `build` | `outputs: [".output/**", ".nuxt/**"]` | результат сборки восстанавливается из кэша |

Полезное:

```bash
pnpm turbo run typecheck --dry           # что возьмётся из кэша, что запустится — без запуска
pnpm turbo run typecheck --graph=graph.html  # граф задач
pnpm graph                               # граф пакетов в браузере (turbo devtools)
```

Изменение `packages/eslint-config` перезапускает typecheck во всех пакетах: turbo считает его обычной зависимостью. Это осознанная цена за честные зависимости.

## Частые ошибки

| Симптом | Причина |
|---------|---------|
| `WARN Cannot extend config from @multi/...`, компоненты слоя не находятся | у слоя нет `"main": "./nuxt.config.ts"` или он не добавлен в зависимости через `workspace:*`. Это только предупреждение — typecheck зелёный, смотри лог dev-сервера |
| `layouts`/`components`/`pages` слоя не подхватываются | лежат не в `app/` слоя (в Nuxt 4 при наличии `app/` всё ищется внутри неё) |
| CSS слоя не находится (`~/assets/...`) | `~` в конфиге слоя указывает на `app/` того, кто запускается. Пути строим от файла: `fileURLToPath(new URL('./app/...', import.meta.url))` |
| клиент падает с `does not provide an export named 'default'` | закомментирован `app.config.ts` (или другой автоподхватываемый файл). Такие файлы удаляем, а не комментируем |
| `"eslint" не является командой` в каком-то пакете | у пакета нет `eslint` в `devDependencies` |
| `Different instances of plugin "import"` | у `@nuxt/eslint` нет `standalone: false` (в т.ч. в `.playground` ui) |
| после переноса файла импорт стал `../../../../packages/utils` | IDE переписала импорты при Move — вернуть `@multi/utils` |
