# Как устроен multiple-apps

Гайд для того, кто открыл репо впервые: какие бывают пакеты, куда класть код и почему что-то «не подхватывается».

---

## Три вида пакетов

| Вид | Кто | Как узнать | Как подключают |
|-----|-----|------------|----------------|
| **Приложение** | `apps/portal`, `apps/f1` | запускается через `dev:*`, есть страницы | f1 — ещё и слой для portal (`extends`) |
| **Слой** | `packages/shell`, `packages/ui` | сам не запускается, вход пакета — `nuxt.config.ts` | `extends: ['@multi/shell']` |
| **Библиотека** | `packages/utils`, `packages/eslint-config` | обычный TS/JS без Nuxt | `import ... from '@multi/utils'` |

Вход пакета (`main` или `exports` в `package.json`) отвечает на вопрос «какой файл получит тот, кто обратится к пакету по имени». У слоя это `nuxt.config.ts`, у библиотеки — `index.ts`. Поэтому в `extends` можно писать только слои.

### Роли слоёв

```
  portal              ← рут: подключает приложения, своих страниц нет
  f1, ...others       ← приложения: только свои страницы, под своим префиксом
  shell               ← каркас: UApp, layout, страница выбора приложения, общие модули
  ui                  ← кит: Nuxt UI, Tailwind, тема (app.config), общие компоненты
```

Аналоги в orders-ui: `ui` = `packages/ui`, `shell` = `apps/guard`, `portal` = корневой `nuxt.config.ts`.

## Куда класть код

Главный вопрос: **«это нужно всем приложениям или только этому?»**

| Что | Куда |
|-----|------|
| компонент, стиль, тема для всех | `packages/ui/app/...` |
| каркас, layout, плагины, «поведение платформы» (например, уведомление о новом релизе) | `packages/shell/app/...` |
| страница приложения | `apps/<app>/app/pages/<app>/...` — **всегда под своим префиксом** |
| layout приложения (меню и т.п.) | родительская страница `apps/<app>/app/pages/<app>.vue` с `<NuxtPage />` внутри |
| компонент только для одного приложения | `apps/<app>/app/components/<app>/...` → имя `<F1PriceTag>`, не пересечётся с другими |
| утилита без Nuxt | `packages/utils` |
| витрина компонентов кита | `packages/ui/.playground` — наружу не уходит |

Чего **не** кладём в приложения: `app.config` с темой и `app.head` в `nuxt.config`. Внутри portal настройки всех слоёв сливаются в одни, и настройки приложения проиграют или испортят соседям. Заголовок страницы задаём на самой странице через `useHead`.

Регистрация приложения в меню выбора на `/`: каждое приложение добавляет себя в `apps` своего `app/app.config.ts`, массивы из всех слоёв склеиваются.

## Кто побеждает при конфликте

Порядок для portal: `portal → f1` (Nuxt раскладывает `extends` в глубину, повторы отбрасывает).

- Сильнее всех тот, кого **запускаешь**.
- Дальше — первый в `extends` **вместе со всей своей цепочкой**, потом второй.

| Что совпало | Как разрешается |
|-------------|-----------------|
| файл с тем же путём (`app.vue`, `pages/index.vue`, `components/PriceTag.vue`) | побеждает один целиком |
| `nuxt.config`, `app.config` | сливаются по ключам, при конфликте побеждает более сильный |
| массивы в `app.config` | склеиваются |

Посмотреть, откуда взят компонент: `.nuxt/components.d.ts` нужного приложения.

## Зависимости

- **Пакет объявляет всё, что импортирует сам.** pnpm строгий: зависимости shell не видны f1, даже если f1 стоит на shell.
- **Модули Nuxt приходят через слой.** `@nuxt/ui` объявлен в ui, `@nuxt/eslint` — в shell (`dependencies`, не `devDependencies`), приложения их не дублируют. Их находит Nuxt по цепочке `extends`, а не `node_modules` приложения.
- **Команды, которые запускаются в папке пакета** (`eslint`, `vue-tsc`), ищут себя в `node_modules` этого пакета — поэтому `eslint` и `@multi/eslint-config` есть в каждом пакете с `lint`.
- **Версии** — один раз в `catalog` в `pnpm-workspace.yaml`, в пакетах `"catalog:"`.
- Внутренние пакеты — `"workspace:*"`, импорт только по имени пакета, не относительным путём (`../../packages/...`).

Правило «кто запускает, тот и ищет»: запускает Nuxt — он ходит по слоям; запускаешь команду в папке пакета — она ищет в этом пакете и выше до корня.

## Turbo

| Задача | Настройка | Что значит |
|--------|-----------|------------|
| `typecheck` | `dependsOn: ["^typecheck"]` | правка в ui перепроверяет shell, f1, portal |
| `lint` | `inputs` + `$TURBO_ROOT$/packages/eslint-config/**` | lint пакета зависит от своих файлов и от общих правил, но не от кода соседей |
| `lint:fix` | `cache: false` | меняет файлы — кэшировать нельзя |
| `build` | `outputs: [".output/**", ".nuxt/**"]` | результат сборки восстанавливается из кэша |

Полезное:

```bash
pnpm turbo run typecheck --dry           # что возьмётся из кэша, что запустится — без запуска
pnpm turbo run typecheck --graph=graph.html  # граф задач
pnpm graph                               # граф пакетов в браузере (turbo devtools)
```

Изменение `packages/eslint-config` перезапускает typecheck во всех пакетах: turbo считает его обычной зависимостью. Это осознанная цена за честные зависимости.

## Частые ошибки

| Симптом | Причина |
|---------|---------|
| `WARN Cannot extend config from @multi/...`, компоненты слоя не находятся | у слоя нет `"main": "./nuxt.config.ts"` или он не добавлен в зависимости через `workspace:*`. Это только предупреждение — typecheck зелёный, смотри лог dev-сервера |
| `layouts`/`components`/`pages` слоя не подхватываются | лежат не в `app/` слоя (в Nuxt 4 при наличии `app/` всё ищется внутри неё) |
| CSS слоя не находится (`~/assets/...`) | `~` в конфиге слоя указывает на `app/` того, кто запускается. Пути строим от файла: `fileURLToPath(new URL('./app/...', import.meta.url))` |
| клиент падает с `does not provide an export named 'default'` | закомментирован `app.config.ts` (или другой автоподхватываемый файл). Такие файлы удаляем, а не комментируем |
| `"eslint" не является командой` в каком-то пакете | у пакета нет `eslint` в `devDependencies` |
| `Different instances of plugin "import"` | у `@nuxt/eslint` нет `standalone: false` (в т.ч. в `.playground` ui) |
| после переноса файла импорт стал `../../../../packages/utils` | IDE переписала импорты при Move — вернуть `@multi/utils` |
| typecheck слоя падает с `never`, а в приложениях всё ок | слой держится на типах, которые ему подкладывают приложения. Типы `app.config` описываем и для записи (`AppConfigInput`), и для чтения (`CustomAppConfig`) — см. `packages/shell/app/app.d.ts` |
